## 1. UX・操作性（9件）

### [P0/M] UX-1 — 未保存のままウィンドウを閉じる/Cmd+Q/プロジェクトを開く操作で、警告なしに編集内容が消失する

- **問題**: 未保存確認（confirm）が存在するのは「ホームへ戻る」ボタンの1箇所のみ。ウィンドウの閉じるボタン・Cmd+Q・メニューの終了では何の警告もなくアプリが終了し、数時間の編集が無言で消える。さらに「開く」ボタン/Cmd+O/メニューの「プロジェクトを開く」も dirty チェックなしで setProject() が現在のプロジェクトを即座に上書きする。動画編集は1セッションが長くデータ量も大きいため、非エンジニアのペルソナAにとって作業消失は致命的で、レビュー/SNSで最も叩かれやすい欠陥。既存の confirm もOK=破棄の2択で「保存して戻る」選択肢がない。
- **根拠**: packages/core/main/main.js:81（mainWindow.on('closed') のみで 'close' の preventDefault なし。before-quit ハンドラも beforeunload も grep でリポジトリ内に存在しないことを確認）／ packages/core/renderer/js/app.js:110-113（btnHome だけ getUI().dirty を confirm）／ packages/core/renderer/js/project-io.js:26-46（openProject→openProjectPath が dirty 確認なしで setProject+clearDirty）／ app.js:126,303（btnOpen と Cmd+O が openProject を直呼び）
- **修正方針**: main で mainWindow.on('close') を preventDefault し、renderer に dirty 状態を問い合わせる IPC（preload は追加のみ可の契約なので新チャネル追加でOK）→ dialog.showMessageBox で「保存して終了／保存せず終了／キャンセル」の3択。openProject()/menu-open の先頭にも同じ3択ガードを追加。btnHome の confirm も同ダイアログに統一する。

### [P1/S] UX-2 — ホーム画面表示中はトーストが背面に隠れ、起動時のFFmpeg警告や「最近のプロジェクト」読込失敗が完全に見えない

- **問題**: .toast は z-index:200、#homeScreen は z-index:1000 かつ不透明背景（radial-gradient）なので、ホーム表示中に発行された toast は全て見えない。具体的に踏む経路が2つある: (1) 起動直後（showHome() の後）に checkTools で FFmpeg 欠落を toast 通知するが、ユーザーには何も見えず、編集画面に入ってから書き出しで初めて失敗する。(2) ホームの「最近のプロジェクト」をクリックしてファイルが移動済みだった場合、「読み込みに失敗しました」toast が背面に出るだけで、ユーザーから見ると『クリックしたのに何も起きず、一覧から項目が消えた』という不可解な挙動になる。
- **根拠**: packages/core/renderer/styles/main.css:272（.toast z-index:200）と main.css:309-311（#homeScreen z-index:1000・不透明背景）。index.html:179,182 で #toast と #homeScreen は兄弟要素（toast が先）であることも確認／ packages/core/renderer/js/app.js:63-68（showHome() 直後に FFmpeg 欠落 toast）／ project-io.js:34-35（openProjectPath 失敗時 toast+removeRecent。app.js:102 の recents クリックから呼ばれ、失敗時 renderRecents() で項目が一覧から消える）
- **修正方針**: 最小修正は .toast の z-index をホームより上（例:1200）へ上げる。加えて recents 読込失敗はホーム画面内にインラインでエラー表示（「ファイルが見つかりません: <path>」＋一覧から削除するか確認）する方が親切。

### [P1/M] UX-3 — 素材ファイルのリンク切れを検出・再リンクする導線がなく、プレビューとエラー文言が誤った原因（FFmpeg欠落）を案内する

- **問題**: プロジェクト読込時に media[].path の存在チェックが一切なく、素材を移動/リネーム/削除しただけで壊れる。その際の表示が二重に不親切: プレビューは「FFmpeg が見つからない可能性があります」と無関係な原因を提示し、書き出しは FFmpeg stderr の生ログ末尾（英語の 'No such file or directory' 等）をモーダルに表示する。ペルソナA（非エンジニア）は自分がファイルを動かしたことと結びつけられず、「壊れた」と判断して離脱する。ファイル整理は普通の行動なので発生頻度は高い。
- **根拠**: packages/core/renderer/js/project-io.js:33-46（openProjectPath はJSONパースのみで素材パスの存在確認なし）／ packages/core/renderer/js/preview.js:507-509（fferror 時に『FFmpeg が見つからない可能性があります（書き出しにも必要）』と表示）／ packages/core/main/export.js:562-564（stderr 末尾12行をそのまま error として返却）→ renderer/js/export-ui.js:236-238（それを400字までモーダル表示）
- **修正方針**: プロジェクト読込直後と書き出し開始前に素材パスの存在チェック（fs.existsSync する小さな IPC を追加）を実行。欠落があれば「◯件の素材が見つかりません」モーダルで一覧表示し、各行に『ファイルを選び直す』（open-file-dialog で path 差し替え）と『無視』を用意。preview.js の fferror 文言も『素材ファイルが見つからない/読めない可能性』を第一候補に変更。

### [P1/S] UX-4 — 書き出し中もキーボードショートカットが全て生きており、Cmd+E の再入で二重書き出し・キャンセル不能状態になる

- **問題**: exportModal はポインタ操作こそ遮るが、wireKeyboard はモーダル表示中かを一切見ないため、書き出し中に Cmd+E を押すと runExport が再入し、保存ダイアログが進捗モーダルの上に出る。続行すると main の 'export' ハンドラが並走し、currentExportProc（単一スロット）が2本目の ffmpeg で上書きされるため、キャンセルボタンは1本目のプロセスに届かなくなる（1本目が完走して出力を書き続ける）。さらに2本目の開始時に exportCanceled=false へリセットされるため1本目のキャンセル状態も失われる。また Space で背後の再生が始まり書き出し中に音が鳴る、S/Backspace 等でタイムライン編集も可能。長時間処理の最中に不可解な並行動作が起きるのはペルソナA/B双方の信頼を損なう。
- **根拠**: packages/core/renderer/js/app.js:289-330（wireKeyboard にモーダル/書き出し中ガードなし。304行で Cmd+E→runExport、312行で Space→togglePlay、315-316行で Backspace/S 編集）／ packages/core/renderer/js/export-ui.js:160（runExport に実行中フラグなし）／ packages/core/main/main.js:355-370（exportCanceled と currentExportProc が単一グローバルで、358行のリセットと364行の registerProc 上書きにより並走時に破綻）
- **修正方針**: export-ui.js にモジュールスコープの exporting フラグを追加し runExport 先頭で return。wireKeyboard 先頭で「exportModal が表示中なら Escape 以外を無視」する1行ガードを追加（文字起こしモーダルにも同時に効く）。main 側も export 実行中の二重 invoke を { ok:false, error:'書き出し中です' } で弾く。

### [P1/S] UX-5 — 文字起こしの「キャンセル」が実際には処理を止めず、後から予期せぬテロップが大量挿入される

- **問題**: キャンセルボタンは cancelTranscribe()（whisper プロセスの kill のみ）とモーダル非表示を行うだけで、renderer 側の runTranscribe フローは中断されない。音声抽出（extractAudio）フェーズ中に押すと kill 対象がまだ無く（currentProc は whisper 起動後にしか登録されない。extract-audio IPC ハンドラ側にも proc 登録なし）何も止まらず、その後 whisper が起動して数分間CPUを消費し続け、完了すると importSrtText が実行されて『キャンセルしたはずの文字起こしテロップ』が突然タイムラインに現れる。長時間処理のキャンセルが信用できないのは、1.5GB の Whisper 同梱を売りにする本製品の中核体験の欠陥。
- **根拠**: packages/core/renderer/js/transcribe-ui.js:95-98（cancel は cancelTranscribe+hideModal のみ、フロー中断フラグなし）・63-79（extractAudio→transcribe→res.ok なら無条件に importSrtText）／ packages/core/main/transcribe.js:155-156（cancel は currentProc のみ kill）・180（currentProc の登録は runWhisper 開始時＝抽出中は null）／ main.js:209-211（extract-audio ハンドラに proc 登録なし）
- **修正方針**: transcribe-ui.js にキャンセルフラグを追加し、cancel 時に立てて extractAudio/transcribe の await 後に必ずチェックして結果を破棄。main 側は extractAudio の ffmpeg プロセスも registerProc 方式で kill 可能にし、cancel-transcribe で両方止める。

### [P2/S] UX-6 — 実行時の予期しないエラーが window.__errors に溜まるだけで、ユーザーには一切表示されない

- **問題**: error-collector.js は error / unhandledrejection を配列に push するのみ（スモークテスト用）。編集操作中に例外が起きても画面は何事もなかったように見え、実際には Undo 履歴の欠落やボタン無反応などの形で静かに壊れる。ai 版では mcp-bridge / chat-panel の動的 import 失敗も console.log のみで、ペルソナB が期待する MCP 接続やチャットFABが『理由の説明なく存在しない』状態になる。
- **根拠**: packages/core/renderer/js/error-collector.js:3-8（push のみで UI 通知なし）／ packages/core/renderer/js/app.js:44-51（mcp-bridge / chat-panel の import().catch が console.log のみ。46行・50行）
- **修正方針**: error-collector.js（またはapp.js）で window error / unhandledrejection 時に toast('予期しないエラーが発生しました…', 'err') を発火（連発防止のスロットル付き）。mcp-bridge/chat-panel の読込失敗は機能名入りの err トーストに昇格する。
- **検証時の補正**: コード事実は evidence 通り（error-collector.js:3-8 は push のみ、app.js:46/50 は console.log のみ）だが priority を P1→P2 に修正。この問題は「他の欠陥が実際に発生した場合」にのみ顕在化するエラー通知の衛生問題で、UX-2〜5 のようにユーザーが決定的に踏む具体的導線がない。通常動作では何も壊れないため、体験を直接損なう P1 群とは重みが異なる。

### [P2/S] UX-7 — トーストが単一スロットの上書き式で、連続通知（読込成功＋スキップ等）の先発メッセージが読めずに消える

- **問題**: toast() は同一 DOM ノードの textContent を書き換えタイマーもリセットするため、連続呼び出しでは最後の1件しか見えない。実際に importMedia は成功件数トーストとスキップ件数トーストを連続で発行しており、混在ドロップ時に「◯件読み込みました」が一瞬で err 表示に置き換わり、成功したのか失敗したのか分からない。操作フィードバックをトーストに全面依存しているアプリなので、この取りこぼしは体感品質に直結する。
- **根拠**: packages/core/renderer/js/ui.js:4-16（単一 #toast ノードへの上書き＋clearTimeout）／ packages/core/renderer/js/media.js:165-166（added と skipped の toast を連続発行）
- **修正方針**: importMedia 側は「3件読み込み・1件は非対応形式でスキップ」の複合1メッセージに統合。恒久策としては toast をスタック表示（最大2〜3件を縦に積む）に変更する。

### [P2/S] UX-8 — 範囲選択中の書き出し確認ダイアログで「キャンセル＝全体を書き出す」という直感に反する2択になっている

- **問題**: 範囲選択がある状態で書き出すと confirm(『選択範囲◯秒のみを書き出します。（キャンセルすると全体を書き出します）』) が出るが、「キャンセル」を押した人の期待は書き出しの中止であり、全体書き出しへ進むのは想定外の破壊的分岐。中止したい場合はこのダイアログに選択肢がなく、次の保存ダイアログを閉じるしかない。また範囲選択モードを解除し忘れたまま Cmd+E した際に、意図せず部分書き出し/全体書き出しへ誘導される事故の温床。
- **根拠**: packages/core/renderer/js/export-ui.js:177-181（confirm の2択で cancel=range無効化＝全体書き出し続行。180行）
- **修正方針**: OS confirm をやめ、既存 exportModal を流用した3択（『選択範囲のみ』『全体』『中止』）に変更。書き出し設定ポップオーバーにも「範囲のみ書き出す」表示を出して状態を可視化する。

### [P2/S] UX-9 — 長さを取得できなかった素材が「読み込みました」成功表示のまま長さ0のクリップとして黙って追加される

- **問題**: ffprobe と HTML5 video の両フォールバックが失敗した動画/音声（破損ファイル・特殊コーデック等）は duration=0 のまま media 登録され、makeClipFromMedia が out:0 のクリップを生成する。タイムラインには幅6pxの謎の細片が置かれ、書き出しペイロード構築時に clipDur<=0.02 で無言スキップされる（該当クリップしか無い場合のみ runExport 冒頭の duration<=0 チェックで「書き出す内容がありません」toast が出るが、他素材と混在時は完全に無言）。にもかかわらず toast は「1件の素材を読み込みました」と成功を報告するため、ペルソナAは『追加したのに再生も書き出しもされない』理由に辿り着けない。
- **根拠**: packages/core/renderer/js/media.js:148-154（probe 失敗時 meta.duration が undefined→duration||0=0 で登録）・165（成功 toast）／ packages/core/renderer/js/state.js:355-359（out: media.duration || 0）／ timeline.js:170（幅 Math.max(6, ...) の細片描画）／ export-ui.js:101,134,148（buildExportPayload が clipDur<=0.02 を無言除外）・163（duration<=0 時のみ toast）
- **修正方針**: importMedia で動画/音声の duration<=0 を検出したら追加を中止し「この形式は読み込めませんでした（◯◯.mp4）」と err トーストで明示。読み込むだけは許す場合もタイムライン追加はスキップして警告する。
- **検証時の補正**: 問題自体は実在するが evidence の帰属を修正: clipDur<=0.02 の無言除外は main/export.js ではなく renderer 側 export-ui.js の buildExportPayload（101・134・148行）で行われる。main/export.js 内の 0.02 は Math.max(0.02, ...) のクランプでありフィルタではない。また 0 長クリップが唯一の素材の場合は runExport:163 の duration<=0 チェックで toast が出るため、「無言」となるのは他素材と混在するケースに限られる点を detail に追記。priority/effort は妥当なので据え置き。

## 2. 機能ギャップ（競合比較）（10件）

### [P0/M] FG-1 — 未保存のままウィンドウを閉じてもデータ消失を防げない（クローズガード・自動保存が皆無）

- **問題**: ウィンドウの close イベントに dirty チェックがなく、ウィンドウ×ボタンや macOS の Cmd+Q（メニュー role:'quit'）で未保存の編集が警告なしに全消失する。dirty 確認は「ホームへ戻る」ボタンの confirm 1箇所のみ。自動保存・クラッシュリカバリも存在しない（renderer/main 全体で setInterval は録音タイマー recorder.js:43 のみ、autosave/beforeunload/before-quit のコードは 0 件）。保存習慣のない非エンジニアのペルソナA が長時間のテロップ作業を失う事故が高確率で起きる。
- **根拠**: packages/core/main/main.js:81（mainWindow.on('closed') のみ。close での preventDefault＋確認なし）/ main.js:100・115（メニューの role:'quit' が無確認で終了）/ main.js:418-420（window-all-closed。即 quit は非 macOS のみだが、ウィンドウ破棄時点で renderer の未保存状態は両OSとも消失）/ packages/core/renderer/js/app.js:110-113（dirty 確認は btnHome の confirm のみ）/ project-io.js:7-24（保存は明示操作のみ・自動保存機構なし）
- **修正方針**: ①main.js の close イベントで preventDefault し、renderer に dirty を問い合わせ（preload は FROZEN だが追加は可）、未保存なら「保存して終了/保存せず終了/キャンセル」ダイアログを出す。②dirty 時に 60〜120 秒間隔で userData 配下へ自動バックアップ（.tceproj.autosave）を書き、起動時に検出したら復元を提案する。既存の writeFile IPC と JSON シリアライズで実装可能。
- **検証時の補正**: ①effort を S→M に修正: close ガード（main↔renderer の IPC 往復＋preload API 追加）＋自動保存＋起動時復元の3点セットはプロセス横断の実装で S では収まらない。②evidence の細部を修正: main.js:418-420 の window-all-closed で即 quit するのは非 macOS のみ（if (process.platform !== 'darwin')）。macOS では menu の role:'quit'（main.js:100）が無確認終了の経路。データ喪失という結論と P0 は不変。

### [P1/M] FG-2 — 動画クリップの音量調整が UI にも書き出しにも存在しない（声と BGM のバランス調整が片側しかできない）

- **問題**: 音量スライダーは kind==='audio' のクリップ限定で、動画クリップの音声は調整不可。書き出しでもベーストラックの動画音声には volume フィルタが一切かからず常に 100% 固定（audioClips 側のみ volume 適用）。トーク動画に BGM を敷く最頻ワークフローで「声が小さい動画を上げる」「PIP 動画の音を下げる」ができず、BGM 側を下げる片側調整しか手段がない。CapCut/Vrew/Filmora では全クリップ音量調整が基本機能で、乗り換え直後に必ず気づく欠落。
- **根拠**: packages/core/renderer/js/inspector.js:109-114（「音量（音声のみ）」で kind==='audio' 限定）/ packages/core/main/export.js:343（ベースクリップの音声フィルタは atrim+asetpts+atempo+apad+afade のみで volume なし）と export.js:475-483（audioClips のみ volume= 適用、483行）/ preview.js:136（ベース動画の volume はフェード係数 clipFadeAlpha のみ）/ export-ui.js:136（非ベース動画は clip.volume を audioClips に載せて書き出し済み＝UI だけ欠落）
- **修正方針**: ①inspector.js の音量セクションを video クリップにも表示（clip.volume は非ベース動画で既に export-ui.js:136 が読んでいる）。②main/export.js のベースセグメント音声フィルタ（343行）に volume= を追加し、preview.js の syncBaseVideo で video.volume に clip.volume を乗算。③MCP/チャットからも触れるよう set_telop と同型の set_clip ツールに含める（FG-7 と合わせて）。

- **修正方針**: stdout の data イベント内でサンプルを逐次バケットに畳み込む（総サンプル数は ffprobe の duration×PR から予測、端数は最後に補正）。メモリは O(buckets) に落ちる。あわせて ensureWaveform 側に同時実行数（例2本）のキューを入れる。

### [P2/M] PERF-9 — クロマキーのプレビューが毎フレーム CPU で全ピクセル走査（getImageData＋sqrt）

- **問題**: chroma 有効クリップは drawTransformed のたびにオフスクリーンへ描画→getImageData→全ピクセルで色距離を sqrt 計算→putImageData を行う。720p で約92万px/フレームであり、PERF-3 の常時60fpsループと重なると停止中ですら毎フレーム全ピクセル処理が走り、クロマキーを1つ置いただけでプレビュー全体がカクつく。オプトイン機能のため P2 だが、機能を試したペルソナAが「重い」と判断する導線になる。
- **根拠**: preview.js:246-252（drawTransformed 内で毎描画 getChromaCanvas→keyOut）、preview.js:262-271（keyOut: getImageData→for 全ピクセル Math.sqrt→putImageData）、増幅要因: preview.js:545-552（停止中も毎フレーム render）
- **修正方針**: 即効策: 距離を二乗のまま比較して sqrt を除去＋停止中はフレームが変わらないのでキー処理結果の canvas をクリップ・時刻キーでキャッシュ。本命はキー処理を縮小解像度（例1/2）で行うか WebGL フラグメントシェーダ化。PERF-3 の dirty フラグ化だけでも停止中の負荷は消える。
